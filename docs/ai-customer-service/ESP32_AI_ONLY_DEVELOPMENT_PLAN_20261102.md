# ESP32 全 AI 交互开发计划

日期：2026-11-02。开发分支：`Dev`。本计划用于安排 Server、设备网关和 Vue 3 管理端的后续开发，ESP32 的服务模式固定为 AI 交互。

目标是让已绑定的 ESP32 稳定完成语音问答、授权设备工具调用和会话恢复，并在当前 Server 中管理设备、查看历史和追踪故障。现有 ASR、Opus 与 TTS 能力继续复用，逐步接入统一 AI 编排。

## 需求范围

### 本期交付

- 修复设备视觉接口鉴权，补齐设备协议边界和兼容测试。
- WebSocket 设备在线注册、能力发现、状态查询、远程命令及结果确认。
- 将新产生的设备对话纳入统一会话，建立可信的设备、账号、智能体和会话映射。
- 让设备语音接入统一 AI 任务与工具执行，保留打断、超时和撤权保护。
- Vue 3 设备管理、会话历史、工具审计和故障诊断。
- 弱网、断线、长时间使用、OTA 和灰度回退验收。

### 服务模式

ESP32 会话设置为 `ai_only`，从设备会话策略约束允许的操作。设备没有转人工、人工排队、专家呼入、真人音视频或人工截图标注流程。共享系统中的 App 客服功能继续按自己的会话策略工作。

管理人员可以配置设备、查看记录、发起获授权的测试和维护操作；这些操作属于设备管理。AI 无法处理的问题，应说明能力或数据限制，并允许用户重试、补充描述或结束当前轮次。

### 独立接入项

真实 Laravel 订单、工单、遥测和知识 API 继续作为独立业务集成。设备基础 AI 交互、MCP 状态和本机音量控制可以先完成。摄像头功能按板卡能力启用，不作为无摄像头设备的上线前提。

## 目标链路与迁移方式

正式链路为：ESP32 发送 Opus → Python 设备网关完成 VAD 与 ASR → Server 验证设备会话并创建唯一 AI 任务 → AI Worker 调用模型 → Java 授权工具执行 → Python 网关转发设备 MCP 并返回结果 → 模型续答 → 网关 TTS 编码为 Opus → ESP32 播放。

Java 负责设备归属、会话与任务状态、权限、工具授权和审计；Python 网关持有真实 WebSocket 连接，负责音频处理、MCP 收发及播放转发。在线目录提供连接定位，持久账本保留命令和对话结果。

迁移分两步：先建立连接管理和设备会话记录，再按设备开启统一 AI 编排。记录旧执行链路时使用专用的可信记录入口，不调用会自动创建新 AI 任务的普通消息发送入口。开启新编排后，该轮只由 AI Worker 请求模型，旧 Python LLM 与旧 MCP 自动执行退出该轮，避免双回复、双扣费和重复控制。

每次会话由服务端决定执行模式，进行中的轮次不热切换执行者。新模式故障明确结束该轮；回退在下一次连接或明确的新会话生效，不自动将未确认的语音重新提交给旧引擎。

## 第一批 安全与协议

优先级：P0。无需真实业务 API，可先使用模拟设备完成。

开发内容：

1. 移除视觉接口按测试客户端标识跳过鉴权的分支。WebSocket 设备 token、视觉上传 token 和内部服务凭据分别检查用途、到期和归属，保留合法客户端兼容。
2. 限制消息体、图片、音频帧、文本和等待队列；规范错误码，日志屏蔽 token、密钥和音频原文等敏感数据。
3. 列出设备与 Server 的协议版本兼容矩阵。当前使用的原始 Opus 帧为首要回归路径；固件支持的 v2/v3 封装，先明确解析与边界规则，再启用。暂未支持的版本在握手时明确拒绝。
4. 校验 `hello` 中的编码、采样率、声道和帧时长，拒绝截断包、错误长度和不支持的参数；保留 `hello/listen/abort/mcp/ping` 合法语义。
5. 增加设备 token 撤销、解绑及停用后的授权版本检查，阻止旧连接继续输入、执行命令和输出语音。

验收：未认证视觉上传失败；有效 token 只能用于正确设备和用途；异常帧不触发模型或耗尽队列；旧设备合法语音和 MCP 协议通过；撤权后无新模型调用、设备命令或迟到回复。

## 第二批 WebSocket 设备管理

优先级：P1。连接框架可与第一批协议测试并行；正式接入依赖第一批授权规则。

### 连接与在线状态

- 服务端验证设备凭据，并从现有绑定关系确定 owner 与 agent；账号或租户归属不由设备请求填写。
- 为连接分配 `connection_id`、代次 `generation`、网关实例和有时限的 lease。Redis 保存在线定位及过期信息，数据库保存必要生命周期和审计。
- 同一设备重连时原子替换连接代次；旧网关、旧 lease 和旧回调不能更新新连接状态或下发新命令。
- 区分 online、offline、unknown；网关不可查询时报告 unknown，不把数据库中存在设备等同于在线。
- 缓存本次连接实际发现的 MCP 能力。断开、换板卡或重连后重新发现，不能假设所有设备都有摄像头、背光或相同工具。

### 命令与确认

- 新增设备状态、能力、命令提交、命令查询接口，允许当前设备所有者及获授权管理员访问。
- Java 通过专用内部认证通道定位实际持有连接的 Python 网关，转发获授权的 MCP 请求。
- 命令绑定设备、账号绑定版本、连接代次、请求 ID、幂等键和超时；记录 pending、succeeded、failed、timed_out、canceled、unknown 等结果。
- 已送达、已执行和状态未知分别表达。响应丢失时不向用户宣称成功，也不盲目重发可能改变状态的命令。
- 先实现状态读取和显式音量设置；重启、固件升级、资源地址变更等维护动作不进入本期 AI 工具允许列表。
- MQTT 设备继续使用对应网关，WebSocket 直连设备走实际在线连接；管理入口按可信连接类型选择适配器。

验收：模拟两个网关、设备断线、重复请求、丢失回执和同设备重连；每项命令只能发给当前授权连接，旧代次结果不覆盖新状态，跨账号访问失败。标准 MCP 设备先不要求重刷固件。

## 第三批 统一设备会话

优先级：P1。会话与数据结构可和第二批并行，端到端接入依赖第二批设备身份及连接代次。

开发内容：

1. 建立设备与 `conversation_id`、owner、agent、设备会话的服务端映射，区分设备长会话、网络连接和语音轮次；断线不等于删除对话。
2. 为设备会话持久化 `channel=esp32` 和 `interaction_mode=ai_only` 等策略。服务端拒绝此类会话的人工服务入口，管理端按能力隐藏相关按钮。
3. 为每轮语音建立 `turn_id`、输入顺序、控制版本及执行模式。ASR 文本、助手回复、工具结果和故障均关联同一轮；执行身份和内容来源可追踪。
4. 对输入上报、输出记录和重复回调实现幂等。旧协议无法确定是否已提交的录音不自动重播；恢复时让用户明确重新发起。
5. 先为旧 Python 执行链提供可信记录模式，不触发新 AI Worker。统一编排开启后，再由专用设备输入入口创建正常 `ai_run`。
6. 按 owner 和 agent 读取有界历史，保留角色配置与设备能力；会话列表按设备筛选，管理端显示 AI 轮次、失败原因和用量。
7. 原设备历史继续只读。已有 App 会话不按 MAC、标题或手机号自动合并，也不将旧历史整批灌入模型。

验收：跨用户与解绑后的访问失败；重复上报不增重复消息；断线恢复保持同一可信会话；一次输入只生成一条用户消息和一次有效执行；ESP32 会话始终遵守 `ai_only`。

## 第四批 统一 AI 编排与设备工具

优先级：P1。依赖第二批命令通道和第三批会话模型。

### AI 执行

- 设备 ASR 文本提交到统一 AI 执行入口，生成真实 `ai_run`，由现有 Worker 请求模型。设备网关消费属于当前轮次的回复，进行 TTS 和 Opus 输出。
- 传递服务端验证的设备身份上下文，包含 owner、agent、设备绑定版本、连接代次、设备会话和轮次；不伪造外部 App Principal。
- 扩展现有工具运行绑定与发布检查，使设备任务也能验证当前授权。复用工具参数校验、预算、调用尝试、不可变审计和真实 usage。
- 设备专属角色与模型配置由可信配置提供；配置不支持时返回明确错误，不静默选择其他提供商。

### 首批设备工具

| 工具 | 行为 | 约束 |
| --- | --- | --- |
| `esp32_get_status` | 读取当前设备实际状态 | 必须在线且具有对应 MCP 能力 |
| `esp32_get_capabilities` | 返回本次连接已发现的能力 | 标明连接代次和发现时间，不能将陈旧缓存当实时状态 |
| `esp32_set_volume` | 设置用户明确要求的音量 | 严格范围与 schema；仅当前绑定设备；缺少确认结果时说明状态未知 |

上述名称为拟定的模型侧别名，内部映射到允许的设备 MCP 工具。现有业务 `get_device` 保留业务查询语义。设备自行上报的新工具不能自动获得 AI 执行权限，工具文本和返回内容均按不可信数据处理。

### 打断与异常

- 新语音、用户打断、断线、解绑、停用和任务取消都推进相应控制版本，取消等待中的工具、模型输出和 TTS。
- 每次工具调用、结果回填及语音转发检查任务、轮次、绑定版本和连接代次。音频发送按顺序串行处理，清理旧 TTS 队列，旧结果不能进入下一轮播放。
- 工具等待异步执行，继续处理心跳和打断；调用次数、参数、结果、时间和输出使用现有有界预算。
- 工具不可用、模型故障或业务 API 未配置时给出明确说明；仅记录已实际报告的用量，缺失用量保持未知。

验收：真实模型执行一次设备状态工具并续答，SQL、工具回执与 TTS 文本一致；验证读状态、设置音量、超时、丢失回执和打断。模拟器先完成，真实设备仅按明确测试范围操作。

## 第五批 管理页面与稳定性

优先级：P2。页面契约确定后可提前开发；正式验收使用前四批完整链路。

### Vue 3 与诊断

- 沿用全局蓝色布局，在设备详情查看在线状态、固件、能力、当前 AI 会话、命令回执和工具审计。
- 提供读取状态、明确的音量设置和会话历史入口；维护操作与 AI 工具权限分别管理。
- 展示设备网关、ASR、模型、TTS 分段耗时、任务错误、队列水位、过期 lease 与限流结果；依赖未探测时显示 unknown。
- 增加按设备和账号的连接数、输入长度、工具调用与模型预算限制，超限提供明确反馈。

### 网络与声音

- 覆盖短断线、长断线、网关重启、API 重启、Redis 故障、慢 ASR、模型超时和 TTS 失败。
- 运行至少 30 分钟的受控设备会话或连续交互测试，核对连接、队列、内存及任务收敛；不得自动重播未确认录音或旧回答。
- 单独进行真人唤醒、连续对话、喇叭听感、打断、噪声和回声验收。USB 合成语音和模拟器只能证明对应技术链路。
- 先记录当前设备的首音延迟与 ASR、模型、工具、TTS 的 p50/p95，再制定回归阈值。

### OTA 与灰度

- 回归 OTA 检查、激活、配置、正确板型的固件与资源下载，以及凭据更新后的重连。
- 固件升级与失败回滚使用独立测试设备验证；执行前保留配置和 Flash/NVS 备份，不在常规接口测试中自动升级。
- 先启动使用 Dev 配置的独立设备网关与测试端口，模拟器通过后再切换明确的测试设备。新旧管理端口切换前核对账号、agent、模型配置和设备绑定。
- 设备级功能开关默认关闭，按指定设备灰度。回退保留新增数据和审计，不恢复覆盖整个数据库，不把进行中的轮次切给另一引擎。

## 可选增强

摄像头板卡可在上述基础完成后增加拍照识图：先验证板型、视觉模型、上传鉴权和图片限额，再将图片绑定到当前设备、会话和轮次，持久化证据并由 AI 语音回答。没有摄像头的设备返回能力不支持。

实时 Omni 直连桥接、屏幕网络镜像、业务遥测与报警作为后续独立任务。当前 USB 屏幕镜像继续作为调试能力；需要网络屏幕同步时另定义传输和授权，避免增加语音主链负担。

## 接口与数据设计任务

以下为拟定设计，开发时需形成 OpenAPI、错误码、权限和幂等契约；现有 OTA、设备接口和 App API 保持兼容。

| 接口组 | 拟定用途 | 权限 |
| --- | --- | --- |
| `GET /api/v1/esp32/devices/{id}/status` | 在线、连接代次和状态摘要 | 设备 owner 或获授权管理员 |
| `GET /api/v1/esp32/devices/{id}/capabilities` | 当前连接能力 | 同上 |
| `POST /api/v1/esp32/devices/{id}/commands` | 提交受限命令和幂等键 | 逐设备、逐命令授权 |
| `GET /api/v1/esp32/commands/{id}` | 查询确定结果或 unknown | 命令归属与当前访问权限 |
| 设备会话查询接口 | 查询设备关联的统一会话 | 设备和会话两层归属校验 |
| `/internal/esp32/*` 精确路由 | 注册连接、续约、命令领取与回执、语音轮次事件 | 独立网关认证及设备授权证明、lease 和代次检查 |

计划增量增加连接生命周期、设备会话映射、语音轮次、命令与尝试/回执记录；需要的字段、索引和外键在实施设计中评审。在线路由可使用 Redis TTL，命令与历史结果必须持久化。原设备 token、内部服务密钥和图片访问凭据不进入页面或通用审计内容。

## 数据与完成标准

继续在 `Dev` 开发，数据库只追加经审查的迁移，不删除、清空或重新初始化已有数据库。旧历史、用户、绑定和已有 App 功能保留；写入真实运行环境前备份并核对既有核心记录。固件烧录和设备端点切换另列为实机操作，不包含在本次规划执行中。

完成顺序如下：

1. 第一批通过鉴权、恶意输入及旧协议回归，提交可独立审查的安全修复。
2. 第二、三批通过双网关重连、命令确认、跨账号隔离、会话幂等和 `ai_only` 策略测试。
3. 第四批通过真实模型、真实 Server、工具回执与语音输出全链，确认每轮只有一个 AI 执行者。
4. 第五批通过故障注入、受控长会话、页面和 CI，再进行指定 ESP32 的真人声学及 OTA 专项验收。
